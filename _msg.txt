feat(android): a diagnostics screen, so the log is reachable from the phone

The logger landed a commit ago but nothing showed it. The file is written to the app's
private storage, which no file manager on the device can reach, so from the phone's point
of view the log did not exist. That is the whole reason this screen is here.

The counters sit above the entries, not below them and not in a file. A log with a hole in
it looks complete - every entry on screen is a real entry, they are just not all of them -
so the dropped count has to be read before the entries, or the user concludes the app is
working fine. That is the one conclusion the log cannot support.

The one button copies the report to the clipboard rather than showing the file's path,
because a path in private storage gives the person holding the phone nothing to act on.

Fourteen strings, written in Persian rather than English-in-both-columns. The desktop's
diagnostics page shipped the other way and stayed English inside an otherwise Persian app,
reading as finished.

Two findings worth recording, both from the tests:

- The model was extracted from the screen specifically so it could be unit tested, and it
  held its state as `by mutableStateOf`. That made it untestable: Compose's state delegate
  calls State.getValue(), which needs an initialised composition, so all fifteen tests threw
  a NullPointerException before reaching a single assertion. Extracting logic to test it and
  then putting a framework type back in is worse than not extracting it - the tests looked
  like they covered the model and covered nothing. The model is plain Kotlin now; the
  screen mirrors it into Compose state.

- The test for "the screen admits the log has holes" used to provoke a genuine queue
  overrun, because the counters were read from the global logger. After the writer was made
  fast enough to keep up with a 6000-entry burst, a 20,000-entry burst stopped overrunning
  it - so the test could no longer reach the branch it existed for, and failed. The counters
  now come through the same injection seam as the log, so the condition is supplied directly.

String integrity is checked statically, the same two checks added for the Windows app after
its diagnostics page shipped broken:

- every L(...) / Strings.raw(...) key used anywhere in the UI resolves through the same
  lookup the UI uses, so a typo cannot render its own name on screen
- no string has identical text in both columns unless it is a listed language-neutral term
  (DNS, TTL, KB/s, "USB Tethering" as printed on the phone), and every Persian column
  actually contains Persian characters - which catches both an untranslated value and the
  two columns being swapped

Both were verified by reintroducing the exact bugs: an unregistered key and an English value
in the Persian column were each caught, and both passed again once reverted.

Not verified: this screen has never been rendered. There is no emulator, no adb and no
device on this machine, so unlike the Windows pages it has not been screenshotted. 134
Android tests pass and the debug APK builds; the native windowing layer is the untested
part, exactly as with the Linux GUI.
